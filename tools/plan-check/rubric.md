# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause (Diagnosis section or equivalent), read against every step, control run, and artifact in the repro-evidence block. | The stated cause is consistent with every step of the repro evidence, including any control run, debug trace, or "expected vs. actual" pair: no step in that evidence contradicts it or actively points to a different cause. The diagnosis does not need every sub-detail individually proven to pass (a reasonable inference that fits the whole pattern of evidence, and that the author flags as inference rather than settled fact, is fine) — it fails only when a specific step demonstrates a different trigger or mechanism than the one claimed (e.g. a control run that still shows the bug with the claimed cause removed, or a trace showing a different code path executing). A cause the evidence is wholly silent on, with no step bearing on it either way, is `unclear`. | required |
| scope-bounded | The plan's scope statement (in-scope / not-in-scope lines) and its Files/Approach section, read as a whole against what the issue + repro evidence actually require to fix. | The plan is one bounded change that addresses the diagnosed cause and nothing structurally larger: no rewrite, migration, cross-cutting abstraction, or bundle of unrelated improvements riding along. A plan may legitimately defer a related, larger concern to a follow-up (that is a pass), but it fails the moment the "fix" is reorganized into a redesign, a multi-file campaign, or a new subsystem the issue never asked for. | required |
| executable | The plan's Files and Approach sections. | The plan names a concrete file, module, or area in the repo and a concrete mechanism or ordered approach specific enough that a stranger with repo access could start working (tracing, drafting the named mechanism) without first asking the author a clarifying question about WHAT to do. Pinning the exact function or line name is not required — "drain pending OSC responses in the reattach handshake, before pane input is wired, in the client attach path" is executable even though the exact function is still to be traced. It fails only when the target area or the mechanism itself is left open — vague verbs with no target ("investigate the input stack," "fix it upstream or vendored, whichever is easier," "poke around this weekend") — not when only the precise line is still to be pinned down. | required |
| test-plan-decisive | The plan's Test plan section, read against the repro evidence's steps and artifacts. | The test plan names a concrete, observable pass/fail outcome that maps onto the same trigger the repro evidence used (e.g., "re-run step N, expect exit 0 / the field now reads X" or "the regression test derived from the issue's case passes"). A test plan that only names a feeling ("should feel faster," "seems fixed") or omits any verification step fails. | required |
| honest-unknowns | The plan's Risks/unknowns language (or its absence), read against what the plan has and has not actually verified (per the repro evidence and the diagnosis). | A plan that names at least one real, specific open question or risk it has not yet verified (or explicitly states there are none and why) passes. A plan that reads as fully certain about everything, including points the repro evidence never actually settles, fails. This check never overrides `diagnosis-grounded`: false confidence about a cause the evidence already contradicts is a `diagnosis-grounded` failure, not just an honesty gap. | preferred |
| comms-thread-aware | The plan comment's text, read against the issue's Thread highlights for any explicit maintainer-proposed direction, rejected approach, or open question. | If the thread contains an explicit maintainer direction (a proposed approach, a rejected alternative, or a stated preference), the plan comment must follow or explicitly engage it — silently proposing a different approach with no acknowledgment fails. If the thread contains no such maintainer direction, this check passes by default. | required |
| disclosure-when-required | The repo-facts block's stated AI-use policy, read against the text of the plan comment. | This check only fires when the repo's policy explicitly asks commenters to disclose AI use and its extent. A policy that only asks for human-written, reviewed, or edited comments (with no explicit disclosure ask) does not trigger this check — pass it by default. When the repo does explicitly require a disclosure statement, the posted plan comment text must contain one naming the tool and the extent of assistance; silence fails. | required |

## Verdict rule

Accept only if every `required` check passes. A single required-check fail or `unclear` holds the package at `reject`. `preferred` checks (`honest-unknowns`) are reported but never flip the verdict on their own. `unclear` on any required check is treated as `fail`: a plan whose grounding, scope, executability, test plan, thread-awareness, or required disclosure cannot be verified from the package is not ready to post and build from.
