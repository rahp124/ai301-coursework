# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| environment-recorded | The repro report's environment record, read against the issue's stated target (version, OS, config) in the issue context / repo-facts block. | The report names the concrete environment it ran in (relevant version, OS, and any config the issue turns on). If that environment differs from the issue's stated target, the report says so explicitly. A report with no environment line at all fails, even if everything else about it is strong. | required |
| steps-followable | The repro report's steps section. | The steps are concrete enough that a stranger could re-run them from a stated starting state through to the trigger: exact commands, exact config, or an exact reproduction link — not a paraphrase like "set up the project" or a reference to files/config the reader cannot see (e.g. a private, unshared repo). | required |
| trigger-fidelity | The artifact (output excerpt, log, screenshot, or playground result) read against the specific behavior the issue describes. | The steps taken target the same trigger conditions the issue describes, not an altered or adjacent one (a different input, a different code path, a different error/exit code). This holds whether the outcome is "reproduced" or an honest, evidenced "could not reproduce" of that same trigger — an honest cannot-reproduce that names what was tried and what differed is a pass; a result from a changed trigger, or an artifact that only shows something adjacent to the bug (e.g. the tool running fine), is a fail. | required |
| honest-claim | The claim comment and repro report's stated conclusion, read against the artifacts that back it. | The words claim no more than the artifacts show. A modest, evidenced statement (including an honest cannot-reproduce, or naming a real open question) passes. A confident root-cause diagnosis, a "verified"/"guaranteed" claim, or a stated result that contradicts or overstates its own shown artifact, fails. | required |
| disclosure-when-required | The repo-facts block's stated AI-use policy, read against the text of the claim comment and repro report. | This check only fires when the repo's policy explicitly asks commenters to state that AI was used and to what extent. A policy that merely asks comments to be "written by a human" or "in your own words" (with no explicit disclosure ask) does not trigger this check — pass it by default. When the repo does explicitly ask for a disclosure statement, the posted text must contain one naming the tool and the extent of assistance; silence fails. | required |
| comms-specific | The claim comment's text, read against the issue it names. | The claim names the specific issue and states a concrete, modest next step or investigation plan in the writer's own words. It fails on interchangeable boilerplate (generic flattery, "assign to me", a guaranteed fix or deadline) and on piggybacking on another comment ("same as above, can confirm") instead of standing on its own evidence. | required |

## Verdict rule

Accept only if every required check passes. A single required-check fail holds the package at reject. There are no preferred checks in this rubric — every proof family the eval set tests for gates the verdict. `unclear` is treated as `fail`: evidence you could not find is evidence not ready to post.
